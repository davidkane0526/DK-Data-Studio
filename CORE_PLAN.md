# DK Data Studio Core execution plan

Baseline: DKDS 3.68.66. Formal Phase E freeze baseline: DKDS 3.69.0. Final archive implementation: DKDS 3.69.4. Scope: the reviewed Phase A–E execution sequence is complete; 3.69.1–3.69.4 are bounded post-freeze maintenance and do not reopen the Phase E contract. This file is now the completed execution record for the 3.69.4 archive baseline; new capability work starts from an explicit 3.70.x plan instead of extending a frozen phase silently.

## Engineering constraints

- Preserve the current Core/plugin architecture and the single current Plugin API contract.
- Historical compatibility remains confined to `src/project-importers/compatibility-gateway.js`.
- Change the owning abstraction rather than adding aliases, fallback paths or plugin-specific Core branches.
- Every public Core capability change updates runtime behavior, SDK types, author documentation and a minimal example in the same iteration.
- Every task requires a failing behavioral reproduction, an implementation-level check and a second independent runtime/data-flow/DOM check.
- Desktop and Mobile continue to consume the same host-neutral Core. Platform geometry remains Presenter-owned.

## Execution order

### Phase A — data and cache correctness

Status: implemented in 3.68.67; full repository verification is recorded in the current handoff.

1. Accept typed numeric sequences at Data Model factory boundaries, copy them into the current serializable Artifact representation and reject malformed matrix shapes.
2. Remove the unversioned mutable Artifact Store escape hatch. All canonical changes must pass through versioned Store write operations.
3. Make Pipeline cache identity include owner, stage ID, exact stage version, input revision/fingerprint and normalized parameters.
4. Share one in-flight computation, replace a fulfilled Promise with its resolved value and evict failed Promises so retry recomputes.
5. Make the plugin performance facade call Core exactly once even when the valid result is `null` or `undefined`; a missing required runtime fails explicitly.

Acceptance: typed series/table/matrix behavior; rectangular matrix validation; immutable Store reads; run→runSync; runSync→run; concurrent identical runs; failure→retry; same stage ID under different owners; stage re-registration with a new version; nullish performance results.

### Phase B — deterministic layout ownership

Status: implemented in 3.68.68; deterministic resolver, controller ownership, explicit scroll policies and bounded diagnostics are verified in the current handoff.

1. Define a canonical `LayoutState` that separates user intent (`preferredSize`, `preferredRatio`, placement and collapse intent) from the current effective rectangle.
2. Move Native Mobile split policy into `SplitController`; remove runtime method replacement from `mobile-split-performance.js`.
3. Add a pure `resolveLayout(state, viewport, platformProfile)` that resolves semantic tracks and constraints. Apply a small set of CSS Grid/Flex variables in one frame rather than writing child rectangles individually.
4. Prevent hidden or zero-sized surfaces from overwriting preferred geometry. Restore the preference with viewport clamping when reopened or rotated.
5. Give every registered region an explicit scroll policy, then retire the normal-mode full-subtree layout recovery scan. Keep bounded diagnostics available only on demand.

Acceptance: Desktop placement is unchanged; Mobile portrait/landscape switching preserves the main plot and user placement; closing a region removes its track and handle; reopening restores a bounded size; one panel resize does not scan or resize the whole workspace.

Public `get/list/events/save/restore/Column Buffer/range-read` outputs remain ordinary Arrays; sparse, mixed or dtype-inexact sequences remain lossless Arrays; canonical fingerprints preserve the same logical JSON sequence semantics.

Acceptance: no silent precision change; source buffers cannot be mutated through a read; undo/save/restore retain exact data; scientific export remains full resolution; worker cancellation prevents stale publication.

### Phase D — rendering, data and automation capability

Status: steps 1–5 complete in 3.68.83–3.68.87.

1. Split scientific plot invalidation into data, geometry, Theme paint and selection overlay paths. Implemented in 3.68.83: `react()` is the authoritative data invalidation, `relayout()/resize()` are geometry invalidations, linked Selection uses an in-place selection overlay that does not mutate source trace data or rebuild the SVG tree, and Theme changes repaint existing D3 nodes without routing through resize/full render. The public ScientificPlot/SDK contract is unchanged; see `docs/reports/PHASE_D_INVALIDATION_3.68.83.md`.
2. Reuse stable SVG nodes keyed by `seriesId`; add viewport-first display sampling that preserves endpoints, extrema, NaN gaps, scan segments and source row identity. Implemented in 3.68.84: `scientific/display-runtime.js` owns stable series identity, cached scan-segment/extents analysis, numeric axis summaries and bounded viewport-first min/max-bucket display projection; the D3 renderer reuses trace groups by `seriesId` and marker nodes by original source `pointIndex`. Explicit segment metadata has priority; stable low-count x-direction reversals form automatic scan segments; pathological non-monotonic x falls back to bounded full-run sampling instead of unsafe binary viewport pruning. Display projection never changes Artifact/calculation/copy/export resolution. See `docs/reports/PHASE_D_DISPLAY_SAMPLING_3.68.84.md`.
3. Render large heatmaps through Canvas while SVG continues to own axes, labels, interaction overlays and export composition. Implemented in 3.68.85: `scientific/heatmap-canvas-runtime.js` owns raster analysis, exact source-cell hit testing, Canvas export layer and raster reuse. Regular grids render through one ImageData upload plus one drawImage composition; unchanged matrix/colorscale reuses that raster for Theme and geometry changes. A 500×500 matrix creates 0 SVG cell nodes. Measured Canvas 2D performance is sufficient, so WebGL remains deferred. See `docs/reports/PHASE_D_CANVAS_HEATMAP_3.68.85.md`.
4. Use Theme revision only for raster or computed-style consumers. Implemented in 3.68.86: Core Theme revision subscriptions are restricted to `raster` / `computed-style`; Scientific Chart consumes that selective channel, while Component Appearance and Material Renderer no longer subscribe to the broad Theme event for document repaint. 5. Make UI, scripts and MCP call the same validated domain commands. Implemented in 3.68.87: the existing Plugin Command Registry now routes explicit `domainCommand` registrations through a Core-owned Domain Command Runtime; Studio Kernel `commands.*` and MCP call the same registry rather than separate handlers. Replayable records capture canonical arguments, input Artifact ids with `artifactRevision` and persistence fingerprint, exact command/plugin/algorithm/provider versions, normalized parameters, source/status/timing and output Artifact references. Replay is opt-in, owner-scoped for plugins and revision-checked by default. Data Center formula-derived-column and Transfer Vth constant-current analysis are first-party real consumers. Acceptance: selection-only changes do not replace the SVG tree; a 500×500 heatmap does not create 250k cell nodes; display sampling never affects calculations or data export; Theme changes update Canvas/SVG paint without recomputing science; UI/scripts/MCP use one validated domain-command path and replay fails closed when recorded input revisions no longer match.

- Formal Phase E freeze is accepted in 3.69.0. The project-owner instruction to enter the formal freeze closes the prior device-acceptance gate; this records acceptance and does not reinterpret automated tests as device-observation evidence.

## Deferred decisions

- Do not expose Store-owned typed backing as a second public data model. 3.68.82 uses it only as an internal physical representation for dense exact numeric payloads; public Artifacts and persisted projects remain ordinary JSON-serializable Arrays.
- Do not replace the complete 3.68.76 canonical fingerprint with a partial numeric digest or use either Store-local revision as persistent identity. `artifactRevision(id)` is only an invalidation stamp; `fingerprint(id)` remains the save/restore-stable content identity.
- Do not build a JavaScript absolute-position layout engine; the resolver produces semantic tracks and CSS variables.
- Do not move all computation or plotting to Python. A Python provider remains an optional later execution backend.
- Do not claim Desktop/Mobile visual acceptance from static tests.
